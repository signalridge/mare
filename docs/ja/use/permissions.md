# 権限とサンドボックス

エージェントに何を許可するかを mare がどう決めるかを説明します。権限プリセット、承認、ルール、プロジェクトの信頼、オペレーティングシステムのサンドボックスに加え、保護されないものも扱います。

2 つの仕組みが連携して働きます。サンドボックスは OS によって強制され、起動されたプロセスが書き込める場所、読み取れる場所、ネットワークで到達できる場所を制限します。承認は、サンドボックスを超えるツール呼び出しの前に、mare があなたに確認するタイミングを決めます。どちらも組み込みの `permissions` プラグインが提供しています。このプラグインを無効にすると、mare はフルアクセスで動作します。

## プリセット

プリセットは、サンドボックスのレベルと承認の動作をまとめて設定します。セッションごとに 1 つ選びます。

| プリセット | ステータスバー | サンドボックス | 確認するタイミング |
| --- | --- | --- | --- |
| `read-only` | `READ` | どこでも読み取り可。書き込み不可。ネットワークはブロック (ネットワークを制御できない Windows の既定の層を除く。後述のサンドボックスの節を参照)。 | ファイルの書き込みの前と、サンドボックスが与える以上の権限が必要な操作の前。 |
| `auto` (既定) | `AUTO` | ワークスペースと一時ディレクトリに書き込み可。ネットワークは、オフにしない限り開放。 | モデルがサンドボックスの外に出ようとしたとき、およびサンドボックスで制限されないツールに対して。 |
| `full-access` | `FULL` | なし。 | 明示的な `prompt` ルール、制限ルールが適用される範囲での解析不能なコマンド、危険なコマンド (後述)。 |

```sh
mare --permission read-only          # for this run
mare --yolo                          # same as --permission full-access
```

```lua
-- ~/.config/mare/init.lua
mare.plugin("permissions", { preset = "auto" })
```

セッション内では、`/permission` でピッカーが開き、`/permission read-only` (または `auto`、`full-access`) で直接切り替えられます。`Shift+Tab` は `read-only` → `auto` → `full-access` → `read-only` の順に循環します。`/yolo` は `full-access` に切り替えます。mare は確認を求めます。`/permission log` は何がどう決定されたかとその理由を表示し、`/permission caps` はこのマシンのサンドボックスバックエンドが強制できることを表示します。セッションはプリセットを記録するため、再開すると復元されます。

信頼されていないプロジェクト (後述) では、明示的な CLI フラグプリセット (`--permission` または `--yolo`) が最優先されます。これらが指定されていない場合、通常の `preset` (`--set plugins.permissions.preset=...` による指定を含む) ではなく設定可能な `untrusted_preset` (既定は `read-only`) で起動し、プロジェクトの信頼が取り消された場合もその上限までダウングレードされます。未信頼ディレクトリでは、`Shift+Tab` で `read-only` へ下げる操作 (`full-access` からなど) はそのまま直接切り替わりますが、次の候補が `auto` または `full-access` になる場合は 1 回のキー押下で昇格させず、現在のプリセットを選択した状態で `/permission` と同じピッカーを開きます。`Esc` を押すと現在のプリセットのまま変わりません。明示的に `auto` を選ぶとそのセッションに適用され、`full-access` を選ぶと引き続き確認が求められます。いずれの切り替えもプロジェクトの信頼状態は変更しません。

`auto` と `read-only` では、シェルコマンドは確認なしでサンドボックス内で実行されます。サンドボックスが何かを拒否したためにコマンドが失敗した場合、モデルは、その拒否が示す最小限の追加権限を求めて再試行できます。追加権限は、ネットワークアクセス (特定のホストへの)、パスへの書き込みアクセス、またはすべてです。この再試行ではあなたに確認します。承認はその 1 回の呼び出しにだけ適用され、自動的に再試行されることはありません。

Windows の既定層はネットワークを制御できず、mare はこの不足を拒否せずに受け入れます。`read-only` の約束をできる範囲で守るため、そこでは該当する無制限アクセス (`all` / `danger-full-access`) が明示的に承認済みまたはルールで許可済みでない限り、すべてのシェルツールおよびコマンドツール (`info.command_tool == true`、`bash`、`powershell`、`mare.tool.command` 登録ツールを含む) の実行前に確認します。厳格に拒否したい場合は、`accept_partial` を明示的に設定してください (後述)。

### `auto` のカスタマイズ

```lua
mare.plugin("permissions", {
  preset = "auto",
  writable = { "~/.cache/pip", "/data/scratch" },   -- extra writable directories (must exist; use physical paths, not symlinks)
  deny_read = { "/home/alice/.ssh" },               -- literal absolute paths the sandbox hides from reads
  network = { default = "deny", allow = { "github.com", "*.npmjs.org" } },
})
```

追加の書き込み可能ディレクトリの相対パスは、作業ディレクトリを基準に解決されます。存在しないディレクトリやディレクトリでないものは通知付きでスキップされ、`mare doctor` が警告します。存在してもシンボリックリンクであるもの、またはシンボリックリンクの先にあるものは、スキップされずにサンドボックスのポリシーによって拒否されます。その物理パスを使ってください。`network` は `true` (開放)、`false` (ブロック)、または `allow`、`deny`、`default`、`allow_local` を持つテーブルです。テーブルはローカルのフィルタリングプロキシを通じて強制されます。後述のネットワークポリシーを参照してください。

## 承認

ツール呼び出しにあなたの判断が必要な場合、mare は `Allow <tool>?` というタイトルのダイアログを表示します。理由、作業ディレクトリ、編集の場合は変更のプレビューが示されます。

| 選択肢 | キー | 意味 |
| --- | --- | --- |
| Allow once | `y` | この呼び出しを実行します。 |
| Allow for this session | `a` | この呼び出しを実行し、セッションの残りの間、同じ呼び出しは確認なしで実行します。シェルコマンドでの「同じ」とは、同じコマンド、ディレクトリ、要求されたスコープを指します。`git push` を承認しても `git push --force` は承認されません。 |
| Allow and remember | `A` | ルールを保存して許可します。シェルコマンドでは、ルールは `git push` のような argv のプレフィックスで、ルールファイルに保存されてすべてのセッションで使われます。それ以外のツールでは、このセッションの間そのツールへのすべての呼び出しを許可します。 |
| Deny | `n` | この呼び出しを拒否します。任意で理由を尋ねられ、モデルはツールの結果でそれを読みます。 |
| Deny and stop | `Ctrl+C` | 拒否してターンを終了します。 |

`Esc` は呼び出しを拒否し、ターンは続行します。追加のサンドボックス権限の要求では、選択肢は「このターンの間」か「このセッションの間」になります。一度に表示される承認は 1 つだけです。

呼び出しがサブエージェントによるものである場合、ダイアログにその名前が表示されます。

### 追加権限の申請

`permissions` プラグインは組み込みモデルツール `request_permissions` も登録します ([ツールとシェルモード](tools.md) を参照)。モデルは `additional_permissions` (追加の `read` パス、既存の物理 `write` ディレクトリ、または `network` の真偽値・ホスト許可リスト)、必須の `justification`、`scope` (既定 `"turn"` または `"session"`) を渡して追加権限を事前申請できます。

ユーザーは申請の一部だけを承認することもできます。ツールの戻り値 (`{ permissions, scope }`) には新規承認または再利用された追加権限だけが含まれ、元のプリセットに元々ある権限は省略されます。拒否された申請は何も付与しません。承認された範囲はそのターンまたはセッション内の後続呼び出しで再確認なしに再利用できます。ホスト側のサンドボックス基準が切り替わった場合 (`sandbox/changed`、例: プリセット変更やホストポリシー更新) は、古い権限が残らないよう一時的なターン・セッション付与とセッション承認キャッシュをすべて破棄します。

### 承認ポリシー

承認ポリシーはプリセットとは別のものです。確認が必要になるリクエストをどう扱うかを決めます。

```sh
mare --approval-policy never    # reject every request without prompting
```

- `ask` (既定): あなたに確認します。
- `never`: 確認せずにリクエストを拒否します。サンドボックスは引き続き適用されます。
- `untrusted`: 読み取りだけを行うものを除き、サンドボックスが許可する場合でも、すべてのツール呼び出しの前に確認します。
- テーブル `{ mode = "granular", categories = { tool = true, network = true } }`: 列挙したカテゴリでのみ確認を許可し、残りは拒否します。

設定は `mare.plugin("approvals", { policy = "never" })` (RPC `options.set {session_id: "...", values: {"plugins.approvals.policy": "never"}}`, `--set plugins.approvals.policy=never`) または `/approval never` で行います。サブエージェントは、継承したポリシーを厳しくすることしかできません。

### 危険なコマンド

一部のコマンドは `full-access` を含むすべてのプリセットで確認されます。`rm -f` / `--force` と `find -delete` (スクリプトのどこにあっても、ラッパー経由でも検出)、Windows では `Remove-Item -Force`、`del /f`、`rd /s /q` です。ヘッドレス実行では誰も答えられないため、これらは拒否されます。確認なしで通せるのは、そのコマンドそのものを許可するルールがある場合だけです。

```lua
mare.plugin("permissions", {
  dangerous = { rules = { { "git", "push", "--force" } } },   -- add your own argv prefixes
})
```

## ルール

ルールは、一致するコマンドに対する判断を固定します。ルールは解析済みのコマンドに対して照合されます。`&&`、`||`、`;`、`|` でつながれたプレーンな語はセグメントに分割され、すべてのセグメントが許可ルールに一致する必要があります。`$(...)`、バッククォート、展開、サブシェル、リダイレクト (`/dev/null` のような固定の出力先を除く)、`eval`、入れ子のシェルを含むコマンドは解析できないため、許可ルールは適用されません。

```lua
mare.plugin("permissions", {
  rules = {
    { argv = { "git", "status" }, decision = "allow" },
    { argv = { "git", "push" },   decision = "prompt" },
    { argv = { "rm", "-rf" },     decision = "forbidden", justification = "never delete recursively" },
    { tool = "my_unconfined_tool", decision = "allow" },
  },
})
```

`decision` は `allow`、`prompt` (常に確認)、`forbidden` (常に拒否) のいずれかです。複数のルールが一致した場合は、最も厳しいものが優先されます。`forbidden`、`prompt`、`allow` の順です。任意のフィールドは、`cwd` (`~/src/**` のようなグロブ)、`scope` (`network`、`write:<path>`、`all`)、`deny_args`、`expires` です。"Allow and remember" で保存されたルールは `~/.local/state/mare/permissions.json` にあり、複数のセッションが安全に共有できます。このファイルを編集するか、`rules_file` を設定して場所を移動できます。

## プロジェクトの信頼

プロジェクトには、mare が読み込みうるコードとプロンプトが含まれることがあります。プロジェクトリソースルート (git ルートまでの範囲で最も近い `.mare/` または `.mcp.json` を含むディレクトリ) にある `.mare/plugins`、`.mare/init.lua`、`.mare/skills`、`.mare/prompts`、`.mare/SYSTEM.md`、`.mare/APPEND_SYSTEM.md` です。信頼プローブは git ルートまでさかのぼって `.agents/skills` も確認しますが、スキル読み込み時に既定の相対スキルディレクトリを解決するのは `mare.project.root` に対して 1 回だけです。プロジェクトリソースはリソースルート自体が信頼されている場合 (かつ開始ディレクトリからルートまでの経路上に拒否がない場合) にのみ読み込まれます。判断は `~/.local/state/mare/trust.json` に保存されます。

```sh
mare trust              # 現在のプロジェクトを信頼 (ディレクトリ指定は mare trust <dir>)
mare trust --revoke     # stop trusting it
mare --trust          # trust it for this run only; saves nothing
mare --no-trust       # distrust it for this run, whatever was saved
```

そのようなリソースがあるディレクトリ (または git リポジトリ内) で初めて mare を開くと、対話 TUI が確認オーバーレイを表示します。発見されたリソースは種別ごとに表示され (`.mare/init.lua` のフル API 実行に関する警告、プラグイン、スキル、プロンプトテンプレート、システムプロンプトファイル、実行ファイル名または URL ホスト名だけにサニタイズした MCP サーバー一覧。6 件を超えるグループがあれば `e` で展開・折り畳み可能)、選択肢は 4 つあります。**Trust and load** (`trust.json` に恒久保存)、**Trust this session only** (保存せずこのセッションのみ読み込み)、**Don't trust** (拒否を保存)、**Not now** (`Esc`、次回再確認) です。ヘッドレスと RPC の実行は尋ねません。`--trust` (今回のみ信頼し保存しない) を渡すか保存済みの信頼がない限り、リソースは読み込まれないままで stderr にメモを出力します。`trust_default` オプション (`ask`、`trust`、`distrust`) は、保存済みの判断がないディレクトリに対する既定動作を設定します。

信頼が対象とするのは、プロジェクトのファイルの読み込みだけです。プロジェクトの MCP サーバーには独自の承認があります。[MCP](mcp.md) を参照してください。

## オペレーティングシステムのサンドボックス

サンドボックスは、ツールのために mare が起動するプロセス (`bash` ツールやその他のコマンドツール) と、mare 自身のファイルプリミティブによるファイルアクセスを、セッションの現在のプリセットで制限します。レベルは `read-only`、`workspace-write`、`danger-full-access` の 3 つです。`workspace-write` では、書き込み可能なルートは、作業ディレクトリ、`--add-dir` または `/add-dir` で追加したディレクトリ (シンボリックリンクを含まず、ホスト保護パス・プロジェクト保護パスと重ならない既存の物理絶対ディレクトリ)、プラットフォームの一時領域、`writable` です。ワークスペース内でも、バックエンドが `fs_protect` を報告する場合は、制限されたプロセスにとって `.git` と `.mare` は読み取り専用のままです (Landlock と Windows の各層は報告しません)。

![3 プラットフォームの OS サンドボックスバックエンドとプローブ能力の比較](../../assets/diagrams/sandbox-backends.svg)

git の linked worktree やサブモジュールで `.git` が既存のポインターファイル (`gitdir: ...`) であるときにコマンドが `write:.git` を要求すると、mare は周囲のワークスペース全体を緩めるのではなく、シンボリックリンクを辿らずに厳格に `gitdir` を解決します。正当な linked worktree (`commondir`、`worktrees/` 配下であること、`objects`/`refs`/`HEAD` 構造、一致する `gitdir` 逆参照を検証) の場合は、ワークツリー固有の `gitdir` とリポジトリ共有の `commondir` の双方に書き込みを許可し、シンボリックリンクや不正な `.git` ポインター・逆参照は拒否します。一方、`.git` 自体が存在しない場合は通常の新規ファイル経路に入り、その既存の親ディレクトリに対する `write` 範囲を要求します (該当する承認は必要です)。

| プラットフォーム | バックエンド | 備考 |
| --- | --- | --- |
| Linux | bubblewrap (`bwrap`)、次に Landlock | `bwrap` がインストールされていて、名前空間を作成できる必要があります。ホストのルートを読み取り専用でマウントし、非公開の `/proc`、`/dev`、PID 名前空間を用意して、書き込み可能なルートをバインドします。ネットワークはネットワーク名前空間でブロックされます。フィルタ付きネットワークは、プロキシにブリッジされたループバック専用の名前空間を使います。`bwrap` が使えない場合は Landlock が使われます。ファイルの書き込みと読み取りは制限され、ソケットは seccomp でブロックされますが、`.git` と `.mare` の保護やドメインのフィルタリングはできません。 |
| macOS | Seatbelt (`/usr/bin/sandbox-exec`) | 書き込み可能なルートを除くファイル書き込みを拒否するプロファイルです。読み取り、外向きのネットワーク、Unix ソケットも制限できます。 |
| Windows、既定の層 | 制限付きトークン、Low 整合性、ACL の付与 | 書き込みは制限されます。読み取りとネットワークは制御されず、mare はこれを部分的な保護として報告します。ネットワーク制御の不足は既定で受け入れられます (上の承認に関する段落を参照)。 |
| Windows、拡張層 | 専用のサンドボックスアカウント、セットアップ時読み取り拒否 ACL、ファイアウォールフィルター | `mare sandbox setup` で一度インストールします (昇格を求められます)。セットアップ時に認証情報およびブラウザーのパスへ読み取り拒否 ACL を設定しますが、`windows-user` バックエンドは呼び出しごとの `fs_deny_read` (および許可リスト型 `fs_read`) を宣言しないため、明示的な `deny_read` を伴う厳格な呼び出しは部分的保護を受け入れない限り拒否されます。ネットワークはフィルタリングされますが、フィルターのプロキシポートはサンドボックス化されたすべての呼び出しで共有されるため、呼び出しごとのネットワーク分離は強制されず、`net_block` や `net_proxy` も報告されません。`mare sandbox status` はセルフテストを実行します。`--require-full` は、すべてが強制されていない限り 0 以外で終了します。呼び出しごとのネットワーク分離が強制されないため、現在はセルフテストに成功しても 0 以外で終了します。`mare sandbox setup --remove` でセットアップを元に戻します。セルフテストに失敗すると、mare は既定の層にフォールバックし、その理由を報告します。 |

mare は各バックエンドを必要に応じてプローブし、実際に動作する機能 (`fs_read`、`fs_deny_read`、`fs_write`、`fs_protect`、`fs_host_protect`、`net_block`、`net_proxy`、`unix_socket`) をキャッシュします。バックエンドにない機能を必要とするプリセットは、弱い設定で実行されるのではなく、その機能名を示した `SANDBOX_INSUFFICIENT` で拒否されます。動作するバックエンドが 1 つもない場合、コマンドは `SANDBOX_UNAVAILABLE` で拒否されます。mare が黙って制限なしで実行することはありません。既定の例外は、`fs_protect` がない場合 (全プラットフォームで受け入れられ、部分的な保護として報告されます) と、Windows の既定の層でネットワーク制御がない場合です。それ以外の不足を明示的に受け入れるには、次のようにします。

```lua
mare.plugin("permissions", { accept_partial = { "network" } })
```

明示的な `accept_partial = {}` は、厳格な拒否を意味します。`mare doctor` で、お使いのマシンのバックエンドと機能を確認できます。セッション内では `/permission caps` です。

### ネットワークポリシー

`auto` では、`network = true` でサンドボックス内のコマンドに対してネットワークは開放されたままになりますが、組み込みの `web_fetch` HTTP クライアントは既定でプライベート・ループバック・リンクローカル・メタデータ IP への接続をブロックします。`false` でネットワーク全体をブロックします。`allow` / `deny` のホストと `default` を持つテーブルを指定すると、トラフィックはホストでフィルタリングするローカルのプロキシを通ります。サンドボックスは、コマンドがそのプロキシにだけ接続できるようにします。ネットワークが制限されている間は Unix ソケットもブロックされます。`unix_sockets` による個別ソケット例外は対応バックエンドでのみ有効です (Linux の seccomp `AF_UNIX` 経路では個別ソケット許可リストに対応していません)。プロキシの環境変数を設定しただけでは、強制とは見なされません。

## 保護されないもの

- 読み取りは既定で開放: `auto` と `read-only` では、`deny_read` または Windows 拡張層の既定対象でない限り、`~/.ssh` を含めユーザーが読めるファイルを参照でき、その内容はモデルプロバイダーへ送信され得ます。
- `network` を変更しない限り、`auto` では外向きネットワークが許可されます。
- `full-access` と承認済みの非制限ツール呼び出しはサンドボックス外で実行されます。`auto` ではローカルサンドボックス外のツール (MCP など) は実行前に確認します。
- Landlock と Windows 既定層は `.git`・`.mare` を保護しません。Windows 既定層は読み取りとネットワークも制御しません。
- サンドボックスは仮想マシンではありません。カーネル・ユーザー・ホームディレクトリを共有するため、`write:.git` の許可はサンドボックス外で実行される git フック変更を可能にします。
- 直接入力した `!cmd` コマンドは承認プロンプトを通過しません。
- プロンプトインジェクション自体は防げないため、`y` を押す前に承認内容を確認してください。
- シェルコマンドによる変更は `/rewind` で戻せません。[セッション](sessions.md) を参照してください。
